Reviewer: independent QA/QC subagent (no implementation context). Branch `claude/practical-cannon-a70ubq` @ `bd028aa`, read-only.
Checks run offline: `npx vitest run tests/unit` → **120/120 pass**; `npm run qc:static` → **pass** (typecheck, lint 0 warnings, prettier, i18n 376 keys EN/TH, art lint). Supabase/app/E2E could not run in this container; everything else below comes from reading code and tests, with file:line evidence.

## Verdict: **FAIL**

There are 2 open S1 and 15 open S2 findings. The worst ones:
- **S1 R-M4-1:** a bedtime push or "Out late tonight" set in the ritual moves the wake target shown in the UI, but the server still judges "I'm up" against the template. Minnie loses the Sunrise ticket the morning after a *planned* deviation.
- **S1 R-M4-2:** the shared `Sheet` moves focus to "Close" every time its parent re-renders. In the Plan day editor that happens on every keystroke, so typing a first-10 or a "Home at" time is effectively impossible on iPhone and Mac. The E2E tests miss it because Playwright's `fill()` sets the whole value in one input event.
- Process gaps (block a "done" ✅ on their own):
  - `docs/qa/M4-report.md` and `docs/qa/M5-report.md` don't exist.
  - The visual baselines for `plan*`/`night*` date from `d3fbf97`, before the M5 backlog, the "feels quick" Plan redesign (215c025) and the Close-today redesign (736a147). CI doesn't run visual tests, so G3 has no evidence for either milestone.

## Flake triage (read-only)

### (a) CJ-07 on ipad-landscape: "YOP chapter 2" never visible after Add item (also seen on ipad-portrait, PROGRESS run #40)

1. **Most likely — the Sheet steals focus during Playwright's `fill()` (same root cause as R-M4-2).**
   - How `fill()` works on a text input: focus + select in one round trip, then `keyboard.insertText()` in a second one.
   - The trigger: `BlockSheet.tsx:18-23` refocuses "Close" whenever `onClose` changes identity. TodayScreen passes a fresh arrow every render (`TodayScreen.tsx:275-279`).
   - TodayScreen re-renders often right when step 3 starts:
     - the 5 `markMissed` upsert responses from step 2 (`useToday.ts:244-246` → `setLogs`);
     - their realtime echoes (`useToday.ts:166-178`), which on a loaded CI runner arrive hundreds of ms to seconds later;
     - the 30 s `useNow` tick (`TodayScreen.tsx:64`).
   - If one of these lands between focus and `insertText`, the text goes to the Close button. `draft` stays `""`, `DayEditor.tsx:273-274` returns early, and nothing is added — exactly "never visible". The test never asserts the input value, so it fails 5 s later at line 54.
   - How to confirm: in the retained trace, the "New checklist item" input is empty and `document.activeElement` is the Close button.
   - Test-first fix: add `await expect(input).toHaveValue("YOP chapter 2")` and an RTL focus-retention test, then fix the Sheet.
2. **Layout shift from SaveStatus.** About 400 ms after the "15 min later" click (`usePlan.ts:15,93`), `SaveStatus` goes from the `sr-only` empty `<p>` to a visible "Saving…" line (`SaveStatus.tsx:4-13`, rendered at `NightRitual.tsx:196`). Everything below moves down about 40 px, right while the test clicks "Work" or "Add item". Playwright's hit-target check usually catches this, so it ranks below #1. A click that lands above "Add item" never submits the form.
3. **The ritual remounts and resets to step 1** if the auto-offered sheet loses `autoOffer` (`TodayScreen.tsx:108,269`). The trigger is `cur` leaving Down, or the date or `nightDoneAtLoad` changing after a refetch. Unlikely in CJ-07, which starts 10 min into a 90-min Down, but it's the same fragile pattern as R-M4-4. To rule it out: the trace would show "Step 1 of 4" at failure time.

### (b) iphone-small "one tap on the circle…": "Finish Wash dishes" never appeared in 30 s

The 30 s timeout (not 5 s) means the page got stuck, not slow. Every path to the button is a serial waterfall with **no retry and no visible error**:

`loadDayContext` (getUser → profiles/settings/templates → day_plans) → `plan.userId` → `useBacklog` select

1. **Most likely — a transient request failure is swallowed and the page stays stuck forever.**
   - If any `loadDayContext` request fails (WebKit-on-Linux "Load failed" or a reset, a Kong 5xx under 2 workers, or `getUser()` returning no user → "signed out" thrown at `loadContext.ts:15`), `usePlan` sets `status:"error"` with `ctx:null`. PlanScreen then shows "Loading…" forever, because the error branch is unreachable (`PlanScreen.tsx:72` vs `:82`).
   - If the backlog select fails, `useBacklog.ts:44-48` sets an error `status` that nothing renders. BacklogList shows "Nothing here yet" (`BacklogList.tsx:353-354`) with no retry.
   - How to confirm: the trace DOM at timeout shows "Loading…" or the empty-backlog text, plus one failed request.
   - Product fix: R-M4-10 / R-M5-4, plus auto-retry.
2. **The auth lock is still held by the page we just left.**
   - The test path: `signIn` returns as soon as the URL is `/today` (`tests/helpers/auth.ts:42`), before Today has settled. It then immediately does REST setup and `goto('/plan')`.
   - At that moment, `ProfileSync`, `useOnboardingState` and `useToday` on /today are all inside `auth.getUser()`.
   - supabase-js serializes session access with `navigator.locks`, using no acquire timeout for `getUser`. If the old WebKit document's lock isn't released promptly during navigation (bfcache/teardown), the new page's `getUser()` waits indefinitely, so it's stuck on "Loading…" with **no** `/rest/v1/settings` request in the trace.
   - Test mitigation: wait for Today's heading or network idle in `signIn`. Product mitigation: a timeout around `getUser`, or use `getSession()` for the user id.
3. **The service worker serves the offline page.** `public/sw.js` answers navigations network-first with an `/offline.html` fallback. A transient navigation error inside the SW (the same WebKit-Linux "internal error" logged as M3-K1) becomes a 200 offline page instead of a `goto` error. The button then can never appear.
   - How to confirm: the trace screenshot is the offline page at URL `/plan`.

Not plausible from the code: the PostgREST `.or(...)` filter (deterministic, other tests pass); the bottom tab bar covering the row (`main` has `pb-[76px+safe-area]`, and the symptom is "not found", not "intercepts pointer events").
